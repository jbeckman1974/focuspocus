# Verification plan

Planning baseline, November 21, 2026, America/New_York. **All acceptance cases below are planned.** This revision contains fixture definitions and expected results. Native runs, application runs, benchmarks, restore drills and pilot results still need evidence.

Use the [parity register](FEATURE_PARITY.md) for requirement definitions, conformance categories and numbered observation tasks. The [architecture](ARCHITECTURE.md) defines the application contract, the [operations plan](OPERATIONS.md) defines operator procedures, and the [project plan](PROJECT_PLAN.md) assigns their milestones.

## How to establish an expected result

1. Use a fresh synthetic workspace for each case and variant. Start with manual order, no focus and no search unless the case sets other options. Record the fixture revision, actor, locale, timezone, clock, selected view, view options, layout, input mode and exact commands. Compare actionable leaf IDs separately from ancestor rows that supply outline context.
2. **Manual** in the tables means the cited Omni Group documentation supplies an expectation. **Observe** means the native result must be captured. Use a disposable database in the native Mac 4.10.1 Pro reference, recording app/build, OS, preferences, before/after ordered IDs, inspector values, times and any relevant screenshots or export. For date-sensitive observations use an isolated test environment with the specified clock, or record the real clock and regenerate equivalent relative dates. Preserve original exports and checksums. Never change the clock or data of a working task database.
3. **Contract** means a proposed product, browser or operations guarantee. Test that guarantee against the relevant project document. On mixed cases, freeze the reference-dependent portion only after native observation. For a mismatch, retain both results and the minimal fixture. Resolve a defect or record the scope and rationale of an accepted difference in [Decisions](DECISIONS.md).
4. Give each execution its own record with AT/FR and variant IDs, evidence basis, input, expected and actual values, build SHA/digest, schema, browser/environment, executor/date and evidence link. Use *not run*, *passed*, *failed*, *blocked on observation* or *accepted exception*. A pass on a prototype or one browser applies only to that recorded variant. A source link supplies no execution result.

Use pure rule tests with an injected clock, API contract tests against real PostgreSQL, and two independent connections for race cases. Exercise transactions through the same command entry points used by the browser. Add browser journeys for focus, input, layout, reconnection and cache behavior. Use manual native comparison, screen readers, real device permissions and cold restores where automation cannot establish the result. Compare the same IDs and effective values across list, detail, search, views, counts and work scheduled from them.

## Desktop accessibility and performance

Proposed support matrix for release qualification is current stable macOS Safari, desktop Chrome, Edge and Firefox, iOS Safari in a tab and as a Home Screen app, and an Android Chrome touch smoke test. Log actual versions at each run. Run selected browser integration tests in Chromium, Firefox and WebKit on CI. Check real Safari/VoiceOver, Firefox/NVDA on Windows, device geolocation and push delivery on a supported mobile installation. Record permission-denied and unsupported states. [S20]

Use WCAG 2.2 AA as the accessibility target. For the core workflow, verify a logical reading/tab order, visible unobscured focus after edits/deletions, labeled controls and tree navigation, announced pending/error changes, selection range, keyboard equivalent for each drag, focus return from menus/dialogs, enlarged text and zoom/reflow (including a 320 CSS-pixel layout), contrast, touch targets and reduced motion. Check rows just outside the virtualized viewport with a screen reader. The M7 gate includes automated checks and successful manual completion of capture, organize, review, conflict resolution and undo. Record defects and retest affected journeys. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)

Use a second deterministic load fixture with exactly 10,000 actions. Generate 100 projects in alternating sequential/parallel mode, with 10 groups of 10 actions each. Number actions 1–10,000. Add tomorrow's defer on multiples of 5, a flag on 7, a held tag on 11, completed state on 13, today's due on 17, and the note token “bench” on 23. Overlaps are intentional. An unscoped Everything search for that token in notes should match 434 actions before changes.

Proposed calibration uses a Linux stack with 4 vCPU, 8 GiB RAM and SSD, an Apple-silicon client with 16 GiB RAM or a documented equivalent, a 1440 × 900 desktop viewport and LAN RTT at most 20 ms. Record exact devices, builds, resource limits, RTT and dataset size. After five warm-ups collect 50 timed samples per interaction on a release build. Alternate common view/search inputs so repeats exercise actual view changes. Measure from input to visible character/selection paint (p95 ≤100 ms) and from view/search input to correct rendered first viewport with counts settled (p95 ≤500 ms). Log cold start and cold queries separately. At M2 require an acknowledged change in one active browser to appear in the second within 5 seconds on this LAN, including after reconnect. Report latency and dropped focus/selection separately. Calibrate on the chosen host before M7 and document changed budgets, hardware or workload in Decisions.
